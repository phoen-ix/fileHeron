## Secrets

`services/secret.py` (policy, create, list, end) + `services/secret_reveal.py`
(reveal); routers `secrets.py`, `public_secrets.py` (ungated, like `public.py`),
`admin/secrets.py`, `admin/settings/secrets.py`; SPA `/secrets`, `/secrets/new`,
`/secrets/:id`, public `/s`. Ships OFF (`secrets.enabled`). → README §Secrets for
the feature surface.

- **The text is readable in exactly ONE place: the reveal response** (`POST /api/secrets/{id}/reveal`, `POST /api/public/secrets/reveal`, both `no-store`). Everything else is built from metadata; `tests/test_secret_no_leak.py` plants a canary and scans every table, log line, webhook, mail and response - extend it, never narrow it.
- **Nothing answering a GET consumes a view, and the token never rides a URL path or query.** Links are `{site}/s#<token>` (a fragment reaches no proxy or access log - an unsubscribe token in a PATH was found in the world-readable Traefik log) and the SPA POSTs the token in a body to `/peek` (free) and `/reveal`; mail gateways fetch links before people do.
- **Ending SHREDS in the same transaction as the state change** (`secret.end_secret`): `ciphertext`, `key_encrypted`, `kdf_*` and every `token_encrypted` go NULL, claimed by a conditional UPDATE on `state = active` so the last reveal and the sweep cannot both end it. `token_hash` stays so an old link answers "gone", not 404.
- **Key layering is instance OUTSIDE, passphrase inside** (`utils/crypto.seal_secret`): a per-secret Fernet data key, wrapped by an Argon2id passphrase KEK when set, then by the instance Fernet. That order is what lets `rotate_jwt_secret.py` re-wrap `secrets.key_encrypted` with no passphrase; `kdf_params` are stored per secret (bounds-checked), so changing `ARGON2_*` strands nothing.
- **A view is ONE conditional `UPDATE ... WHERE views_used < :x` + rowcount on the counter the scope names** (`total` → `secrets.views_used`, `per_person` → the person's `secret_user_states` row, `per_recipient` → the entry's pool; an address or the link always its own row), under a `FOR UPDATE` + `populate_existing()` lock on the secret row (pinned in `test_mariadb_row_locks.py`). The pre-check is not the guard: `test_the_claim_itself_refuses_past_the_limit` drives the claim primitives, because a mutant without the `<` survived every route test.
- **`secret_user_states` rows are written at SEND time for every eligible person** (direct + group snapshot, minus the sender and disabled users), so no counter is ever an insert race.
- **Group eligibility is member-then AND member-now** (`secret_group_members` joined to live `group_members` in `_reach_query`); the sender never is. "Now" alone hands the secret to whoever joins later; "then" alone keeps it readable by someone who left.
- **A direct recipient never draws on a group's pool** (`per_recipient`); a group-only person takes the first of their groups with views left.
- **A wrong passphrase never costs a view and answers 403 `SECRET_PASSPHRASE_INVALID`, never 401** - it is checked BEFORE the claim, and a 401 sends the SPA into refresh-and-replay (`docs/engineering/auth.md`). The attempt is COMMITTED before the raise, or the rollback erases what the throttle counts.
- **Lock mode locks a link/address only on failures from ≥3 distinct IPs** (`MIN_DISTINCT_IPS_FOR_LOCK`, the public-link rule); one source gets 429, an account recipient is throttled per user and never locked. Burn mode's `burn_after_failures` is frozen at create (a stored fact, not a live read of the setting) and ends the secret for that ONE principal.
- **Sender and admins never reveal** (`SECRET_REVEAL_FORBIDDEN`), and admins have no route to a link: `GET /api/secrets/{id}/links` is sender-only, audited `secret_link_shown` each time. Recipients never see the roster, nor the aggregate `views_used` (None for them: in `per_person` it says how often the others looked); account viewers' IPs go to admins only (`_events(show_all_ips=...)`).
- **Two `policy_gate` gates, via its `default_mode` param**: send (default `everyone`; a client still reaches only connected employees) and external = an address or the link (default `employees_admins`). `may_send_external` refuses a client BEFORE the gate, so no mode or allowlist entry lets a client send outside - the admin page's outside side says so and hides clients from its search. Policy-route settings, not registry tunables; the four id lists are in `config_backup._JSON_*_ID_KEYS`.
- **The switch stops SENDING only** (`SECRETS_DISABLED` from `create_secret` and `replace_link`); reveals, the sweep and the admin list keep working, so switching off strands no recipient - burn from the admin list to end them.
- **Expiry is checked in the reveal path itself** (`assert_readable`), never left to the 5-minute `expire_secrets` sweep, which also ends secrets nobody can read any more (left the group, disabled). `max_lifetime_days` caps `expires_at` at create even for a views-only secret, or an unread one lives forever.
- **Email addresses are never looked up** (the share external-recipient rule: an answer would tell the sender a client exists); audit rows carry address COUNTS.
- **Config import burns every active secret** in step 1's committed pass beside the share invalidation; secret tables are never exported. Erasure deletes the secrets the user sent.
- **`secret_recipients.recipient_group_id` is BigInteger** - `groups.id` is BIGINT on MariaDB and InnoDB refuses a mismatched FK (errno 150), which SQLite never notices; `make test-mariadb` caught it.
- **The mail log masks `/s#<token>`** through `_AUTH_LINK_RE` built from `SECRET_LINK_BASE_PATH` (never a literal), and `secret_link_external` is in `_AUTH_LINK_CATEGORIES` (no resend).
- **Secret REQUESTS (`services/secret_request.py`): an answer IS an ordinary secret** whose only reader is the requester (`store_sealed` is the one sealing path for both), so reveal, counting, throttle and shred are unchanged. It must stand alone once the request is pruned: the request's label becomes its label, and `is_answer` (the requester's burn right) and `answered_by_email` live on the secret. `created_by_id` is NULL for an answer through a link - lists OUTER-join the sender, and every sender notice skips a NULL.
- **The first answer wins by a conditional `UPDATE secret_requests ... WHERE state = 'open'` under a `FOR UPDATE` lock on the request row**; the state check before it is not the guard (`test_the_claim_itself_refuses_a_second_answer`). Expiry is checked in the answer path itself (`closed_reason`), never left to the sweep; every other token's `token_encrypted` is NULLed in the same transaction.
- **The requester's passphrase is never stored**: `crypto.request_keypair` derives an X25519 pair from Argon2id(passphrase) and the request keeps only the PUBLIC key; the answer's key is ECDH+HKDF-wrapped to it INSIDE the instance layer (rotation still needs no passphrase). A wrong layer is named (`SECRET_REQUEST_PASSPHRASE_INVALID` vs `SECRET_PASSPHRASE_INVALID`) - only the signed-in requester can ever try one.
- **The requester never answers their own request** - creation cannot make them a target, and `answering_target` refuses them anyway (pinned with a planted row). Asking follows the SEND rules (`may_send`, `may_send_external`, `_validate_recipients`); answering needs no send right, the request is the authorisation.
- **`/r#<token>` is the third fixed link path** (`REQUEST_LINK_BASE_PATH`), masked in the mail log; `secret_request_external` is in `_AUTH_LINK_CATEGORIES`. Config import cancels open requests beside burning secrets; erasure deletes the requester's requests; `prune_history` deletes ended ones after `retention.secret_days`.
- **`SecretDetail.vue` keeps the reveal card mounted after the last view** (`revealedHere`): the metadata reload flips `can_reveal` false, and a bare `v-if` unmounted the text the user had just spent their view on. e2e found it; `SecretDetail.test.ts` pins it.
